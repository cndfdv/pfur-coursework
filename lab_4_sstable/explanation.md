## 1. Зачем нужен ещё один формат хранения

В лабе 3 мы научились надёжно сохранять кэш через WAL. Но WAL — это **журнал событий**, а не **база данных для поиска**. У него есть проблемы для долгосрочного хранения:

- **Дублирование.** Один и тот же ключ может встречаться много раз (если перезаписывали). Даже после компактизации он там как «последняя версия» — но рядом всё ещё лежат логи операций.
- **Неупорядоченность.** Записи лежат в порядке поступления операций, не в порядке ключей. Чтобы найти ключ `user:42`, нужно прочитать всё.
- **Не оптимизирован под чтение.** Формат хорош для записи (последовательное добавление), плох для поиска.

Нам нужен формат, в котором:
1. Каждый ключ встречается **ровно один раз**.
2. Ключи **отсортированы** — это даёт бинарный поиск и удобство сравнения файлов.
3. Файл **неизменяемый** (immutable) — после записи никто его не правит. Можно безопасно читать многими потоками, кешировать, копировать.

Такой формат и есть SSTable.

## 2. Что такое SSTable

**SSTable — Sorted String Table.** Файл, содержащий пары `ключ → значение`, упорядоченные по ключу, неизменяемые после создания.

Термин и реализация впервые появились в **Google Bigtable** (2006). Из-за элегантности модель растащили все современные key-value БД: **LevelDB**, **RocksDB**, **Apache Cassandra**, **HBase**, **ScyllaDB**, **CockroachDB**.

Ключевые свойства:
- **Sorted.** Ключи отсортированы → бинарный поиск, range scan, эффективное слияние двух SSTable как двух отсортированных массивов.
- **String.** Изначально строковые ключи и значения. Сейчас условно — может быть любой сериализуемый тип. В нашей лабе и ключи, и значения — UTF-8 строки.
- **Table.** Просто набор `(key, value)` пар.
- **Immutable.** Один раз записали — больше не меняем. Если данные обновились → пишется новый SSTable, старый со временем удаляется.

### Immutability — это очень удобно

Если файл не меняется:
- Не нужны блокировки на чтение — несколько процессов могут параллельно читать.
- Можно вычислить контрольную сумму один раз и проверять при чтении.
- Операционная система может агрессивно кешировать страницы.
- Реплицировать на другие узлы — просто скопировать файл.

Минус только один: апдейт превращается в «создать новый файл + удалить старый». Это компенсируется compaction-стратегиями (см. ниже).

## 3. LSM-tree — место SSTable в реальных БД

SSTable редко существует сам по себе. Обычно он часть **LSM-tree** (Log-Structured Merge Tree) — архитектуры хранения, оптимизированной под write-heavy нагрузку.

Типичный поток данных в LSM-БД:

```
WRITE:
   клиент → memtable (in-memory, sorted) + WAL (durability)
       │
       │ когда memtable заполнен
       ▼
   flush → SSTable level 0 на диск
       │
       │ периодически
       ▼
   compaction → сливаем несколько SSTable в один большего размера
                на уровень выше (level 1, 2, ...)

READ:
   ищем сначала в memtable, потом по SSTable от свежих к старым
```

Видно, что SSTable, WAL и in-memory кэш — это не три разные задачи, а три кирпича одной системы:
- **In-memory cache (лаба 2)** ≈ memtable. Быстрый, потокобезопасный, поддерживает обновления.
- **WAL (лаба 3)** ≈ durability layer. Защищает memtable от потерь до сброса на диск.
- **SSTable (лаба 4)** ≈ immutable persistent storage. Долгосрочное хранилище, оптимизированное под поиск.

Поэтому курс лабораторных идёт именно в таком порядке.

### Compaction в LSM

С immutable файлами появляется проблема: каждое обновление = новая запись в новом SSTable. Через какое-то время для ключа `user:42` могут существовать 10 файлов с разными версиями. Чтение — это поиск во всех.

Решение — **compaction**: периодически берём несколько SSTable, сливаем их в один (как merge sort двух отсортированных массивов), оставляя только последние версии ключей. Старые файлы удаляются.

Эту часть мы в лабе не делаем — задание про создание одного SSTable и чтение из него. Но важно знать, что в реальности она есть, и она — самая нагруженная часть инженерии LSM-БД (LevelDB, RocksDB предлагают несколько стратегий compaction: leveled, tiered, universal).

## 4. Структура файла: HEADER / DATA / SPARSE_INDEX / FOOTER

Задание требует четыре секции. Это упрощённая, но честная схема реального SSTable.

```
┌──────────────────────────────────────────────┐ offset 0
│ HEADER                                       │
│ ┌────────────────────────────────────────┐   │
│ │ MAGIC (8 байт)        = "SSTB0001"     │   │
│ │ entry_count (u32)     = сколько пар     │   │
│ │ sparse_step (u32)     = шаг индекса     │   │
│ │ data_offset (u64)     = смещение DATA   │   │
│ └────────────────────────────────────────┘   │
├──────────────────────────────────────────────┤ data_offset
│ DATA BLOCKS                                  │
│ ┌────────────────────────────────────────┐   │
│ │ len(K1) | K1 | len(V1) | V1            │   │
│ │ len(K2) | K2 | len(V2) | V2            │   │
│ │ ... (отсортировано по ключу)            │   │
│ │ len(Kn) | Kn | len(Vn) | Vn            │   │
│ └────────────────────────────────────────┘   │
├──────────────────────────────────────────────┤ sparse_offset
│ SPARSE INDEX                                 │
│ ┌────────────────────────────────────────┐   │
│ │ len(K1)   | K1   | offset(K1)          │   │
│ │ len(K65)  | K65  | offset(K65)         │   │
│ │ len(K129) | K129 | offset(K129)        │   │
│ │ ... каждый sparse_step-й ключ           │   │
│ └────────────────────────────────────────┘   │
├──────────────────────────────────────────────┤ конец файла - FOOTER_SIZE
│ FOOTER                                       │
│ ┌────────────────────────────────────────┐   │
│ │ sparse_offset (u64)                     │   │
│ │ sparse_count  (u32)                     │   │
│ │ MAGIC (8 байт)        = "FTR00001"     │   │
│ └────────────────────────────────────────┘   │
└──────────────────────────────────────────────┘ EOF
```

### Зачем magic bytes
`b"SSTB0001"` в начале и `b"FTR00001"` в конце — это «подпись» формата. Любой ридер сначала проверяет их и отказывается работать, если не совпали. Это защита от:
- открытия не того файла (пользователь дал путь к JPG-картинке);
- повреждённого файла (диск сбоил, файл обрезан);
- несовместимой версии формата (когда выпустим SSTable v2, будем знать, что v1 — это `0001`).

### Зачем дублировать metadata в header и footer
- **Header** даёт быстрый доступ к началу данных при последовательном чтении.
- **Footer** — фиксированного размера в самом конце файла. Чтобы быстро найти sparse index, не читая весь файл, мы делаем `seek(-FOOTER_SIZE, SEEK_END)` и читаем только хвост. Это критично для больших SSTable (на десятки гигабайт).

В реальных форматах ещё бывают: bloom filter (быстро отвечает «есть ли вообще такой ключ?»), block checksums (детектирование повреждений на уровне отдельных блоков), сжатие отдельных data blocks. Я их опустил — фокус на основной идее.

## 5. Бинарный формат и `struct`

Все размеры и числа я пишу как фиксированные бинарные поля через модуль `struct`.

```python
HEADER_FMT = "<8sIIQ"
```

Расшифровка формата:
- `<` — **little-endian** (младший байт первый). Прибиваем гвоздями, чтобы файл одинаково читался на любой архитектуре.
- `8s` — 8 байт строки (без длины, фиксированно).
- `I` — unsigned int 32 бита (4 байта).
- `I` — ещё один.
- `Q` — unsigned int 64 бита (8 байт).

Итого `8 + 4 + 4 + 8 = 24` байта на header. `struct.calcsize(HEADER_FMT)` это и подтверждает.

### Почему длина перед строкой

Каждая запись в DATA выглядит так:
```
len_key (4 байта, u32) | key_bytes | len_value (4 байта, u32) | value_bytes
```

Это паттерн **length-prefixed encoding**. Альтернативы:
- **Разделитель** (например, `\0`): не работает для бинарных значений, в которых может быть `\0`.
- **Фиксированная длина**: невозможна, ключи и значения разной длины.
- **Длина впереди**: знаем заранее, сколько байт читать. Универсально, быстро (одна операция чтения с известным размером).

Этот же приём используется в Protobuf, MessagePack, во всех бинарных протоколах сериализации.

### Почему little-endian
Это согласованный выбор. Big-endian был популярен в сетевых протоколах («network byte order»), little-endian — в x86 и ARM. Сейчас почти везде на интерфейсах между сервисами используется little-endian, потому что на нативной архитектуре он не требует разворота байтов. Для пользовательских форматов хранения — тем более.

## 6. Sparse index и бинарный поиск

Это сердце эффективности SSTable.

### Полный индекс vs разрежённый

Простейший вариант индекса — записать в конце файла **каждый** ключ и его смещение в DATA:
```
key1 → offset1
key2 → offset2
key3 → offset3
...
keyN → offsetN
```
Проблема: если у нас 100 миллионов ключей, полный индекс занимает столько же места, сколько данные. Загружать его в память — дорого.

**Sparse (разрежённый) индекс** хранит каждый N-й ключ:
```
key1   → offset1
key65  → offset65
key129 → offset129
...
```
У меня `N = 64` (`sparse_step`). При миллионе ключей в индексе ≈ 15 625 записей — это уже без проблем умещается в памяти.

### Алгоритм поиска ключа K

1. **Бинарный поиск в индексе** → находим самый большой опорный ключ Kᵢ такой, что Kᵢ ≤ K. (Это гарантирует, что искомый ключ, если он есть, лежит в интервале `[offset(Kᵢ), offset(Kᵢ₊₁))`.)
2. **Прыжок в файл** на `offset(Kᵢ)`.
3. **Последовательное сканирование** до `offset(Kᵢ₊₁)`. Среди этих записей либо встретим искомый ключ → возвращаем значение, либо встретим ключ больше искомого (тогда искомого в файле нет — данные отсортированы), либо дойдём до конца блока (тоже значит «нет»).

Стоимость поиска:
- Бинарный поиск по индексу: O(log N/64) сравнений в памяти — мгновенно.
- Чтение с диска: один `seek` + чтение максимум 64 пар (≈ несколько килобайт). Современный SSD это делает за десятки микросекунд.

Это и есть идея sparse index: **обменять немного линейного скана на диске на огромную экономию памяти под индекс**.

### Тонкость бинарного поиска

В коде я ищу «последний элемент ≤ ключ». Это вариант binary search, не самый частый — обычно ищут «равен» или «первый ≥». Реализация:

```python
lo, hi = 0, len(self._sparse) - 1
if hi < 0 or key < self._sparse[0][0]:
    return None                    # ключ меньше минимального — точно нет
while lo < hi:
    mid = (lo + hi + 1) // 2       # верхнее округление!
    if self._sparse[mid][0] <= key:
        lo = mid                   # двигаем левую границу вправо
    else:
        hi = mid - 1
```

Почему `(lo + hi + 1) // 2`, а не `(lo + hi) // 2` (классическое деление пополам): без `+1` при `hi = lo + 1` мы бы выбрали `mid = lo`, и при условии `<=` поставили бы `lo = mid = lo` — бесконечный цикл. С верхним округлением сходимся корректно.

## 7. Разбор кода `sstable.py`

Файл: [sstable.py](sstable.py).

### Запись: `Cache.flush_to_sstable`

```python
def flush_to_sstable(self, path: str, sparse_step: int = 64) -> None:
    items = sorted(self._store.items())
    with open(path, "wb") as f:
        f.write(b"\x00" * HEADER_SIZE)   # резерв
        data_offset = f.tell()

        sparse: list[tuple[str, int]] = []
        for i, (k, v) in enumerate(items):
            offset = f.tell()
            if i % sparse_step == 0:
                sparse.append((k, offset))
            _write_kv(f, k, v)

        sparse_offset = f.tell()
        for k, off in sparse:
            kb = k.encode("utf-8")
            f.write(struct.pack("<I", len(kb)))
            f.write(kb)
            f.write(struct.pack("<Q", off))

        f.write(struct.pack(FOOTER_FMT, sparse_offset, len(sparse), FOOTER_MAGIC))

        f.seek(0)
        f.write(struct.pack(HEADER_FMT, MAGIC, len(items), sparse_step, data_offset))
        f.flush()
        os.fsync(f.fileno())
```

Что здесь интересного:

1. **`sorted(self._store.items())`** — ключевой момент. Без сортировки sparse index и бинарный поиск не работают.
2. **Резерв под HEADER нулями.** Мы не знаем `entry_count` и `data_offset` заранее (они известны только после записи данных), но они должны лежать в начале файла. Решение: пишем 24 нулевых байта, продолжаем как ни в чём не бывало, в конце возвращаемся `f.seek(0)` и перезаписываем настоящий header.
3. **`f.tell()`** — возвращает текущую позицию файлового указателя. Используем, чтобы запомнить, где начинается каждая запись (для sparse index) и где начинается секция SPARSE INDEX (для footer).
4. **`enumerate(items)` + `i % sparse_step == 0`** — простой способ выбрать каждый N-й элемент. Первый, 65-й, 129-й… — каждый попадает в индекс.
5. **`fsync` в конце** — гарантия durability, как в WAL. После возврата метода файл точно на диске.

### Чтение: `SSTableReader.__init__`

```python
def __init__(self, path: str):
    self._path = path
    self._lock = threading.Lock()
    with open(path, "rb") as f:
        header = f.read(HEADER_SIZE)
        magic, entry_count, sparse_step, data_offset = struct.unpack(HEADER_FMT, header)
        if magic != MAGIC:
            raise ValueError("bad SSTable magic")

        f.seek(-FOOTER_SIZE, os.SEEK_END)
        sparse_offset, sparse_count, fmagic = struct.unpack(FOOTER_FMT, f.read(FOOTER_SIZE))
        if fmagic != FOOTER_MAGIC:
            raise ValueError("bad footer magic")

        f.seek(sparse_offset)
        sparse: list[tuple[str, int]] = []
        for _ in range(sparse_count):
            (kl,) = struct.unpack("<I", f.read(4))
            k = f.read(kl).decode("utf-8")
            (off,) = struct.unpack("<Q", f.read(8))
            sparse.append((k, off))
```

Шаги:
1. **Header** — читаем с начала, проверяем magic.
2. **Footer** — `seek(-FOOTER_SIZE, SEEK_END)` прыгает на хвост, узнаём, где sparse index.
3. **Sparse index** — единственная часть, которую мы держим в памяти. Сам DATA-блок не читается. При миллионе записей и `sparse_step=64` это около 15 000 ключей — мегабайты, а не гигабайты.

### Чтение: `SSTableReader.get`

```python
def get(self, key: str) -> Optional[str]:
    # бинарный поиск
    lo, hi = 0, len(self._sparse) - 1
    if hi < 0 or key < self._sparse[0][0]:
        return None
    while lo < hi:
        mid = (lo + hi + 1) // 2
        if self._sparse[mid][0] <= key:
            lo = mid
        else:
            hi = mid - 1
    start_offset = self._sparse[lo][1]
    end_offset = self._sparse[lo + 1][1] if lo + 1 < len(self._sparse) else self._sparse_offset

    with self._lock, open(self._path, "rb") as f:
        f.seek(start_offset)
        while f.tell() < end_offset:
            k, v = _read_kv(f)
            if k == key:
                return v
            if k > key:
                return None       # дальше точно нет
    return None
```

Три кейса завершения:
- Нашли ровно тот ключ → возвращаем значение.
- Прошли ключ больше искомого → возвращаем `None` (ранний выход, экономит чтения).
- Дошли до конца блока → возвращаем `None`.

`_lock` здесь защищает от того, что один и тот же `SSTableReader` могут использовать несколько потоков. Внутри они открывают файл и двигают указатель — это нельзя делать параллельно (получим путаницу в `seek`/`read`).

В реальных БД делают иначе: открывают файл один раз, а на чтение используют `pread(fd, offset, size)` — атомарное чтение по абсолютному смещению без сдвига указателя. Тогда блокировка не нужна. В Python `os.pread` тоже есть, но для учебной задачи `Lock` проще и понятнее.

```python
assert mismatches == 0
```
Это и есть финальная проверка из задания: «при вызове GET возвращает нужное значение». Прогоняем все 10 000 ключей, считаем расхождения. Их должно быть 0.

Заодно меряем скорость — сколько ops/sec даёт чтение. На обычном MacBook получается порядка десятков тысяч в секунду; основная стоимость — открытие файла на каждом `get`. В продакшен-реализации файл держат открытым и используют `pread` — там получаются сотни тысяч ops/sec на одном потоке.
