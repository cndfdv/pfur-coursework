## 1. Проблема: память — это не навсегда

Кэш из лабы 2 живёт в оперативной памяти. У этого есть фатальный недостаток: **смерть процесса = потеря всех данных**. Процесс может умереть по куче причин — кто-то сделал `kill -9`, упало по OOM, паника интерпретатора, перезагрузка машины, отключение питания.

Для настоящих систем это неприемлемо. Если пользователь записал что-то, увидел «ОК» — оно должно сохраниться, даже если сразу после этого сервер выдернули из розетки. Это свойство называется **durability** (буква D в ACID).

Durability требует, чтобы данные перед подтверждением попадали на **энергонезависимое хранилище** — диск.

Самое прямолинейное решение: при каждом `set` перезаписывать весь словарь на диск. Очевидные минусы:
- Медленно: сериализация 1 ГБ кэша при каждом изменении.
- Опасно: упали в момент перезаписи — файл побит, данные потеряны.

Нужен способ хитрее — это и есть WAL.

## 2. Что такое WAL и откуда он взялся

**WAL — Write-Ahead Log**, журнал упреждающей записи. Это **append-only** файл, в который записывается каждая операция изменения данных **до** или одновременно с её применением к памяти.

«Write-ahead» = «пишем заранее»: сначала на диск (журнал), потом в память. Если упадём — журнал на диске остался, можно повторить все операции и восстановить состояние.

WAL — фундаментальная техника. Её используют:
- **PostgreSQL** — буквально называется WAL, лежит в `pg_wal/`.
- **MySQL/InnoDB** — называется redo log.
- **SQLite** — режим WAL (альтернатива rollback journal).
- **Kafka** — топик это и есть WAL для сообщений.
- **RocksDB, LevelDB, Cassandra, HBase** — WAL перед memtable.
- **etcd, ZooKeeper** — журнал решений Raft/Paxos.
- **Файловые системы ext4, NTFS, APFS** — journaling в их основе это тот же WAL.

### Почему append-only

- **Скорость.** Последовательная запись в конец файла — самая быстрая операция дисковой системы. И HDD, и SSD оптимизированы под последовательный поток. Случайная запись в середину файла на порядок медленнее.
- **Простота восстановления.** Файл читается с начала до конца, в порядке операций. Никаких хитрых индексов, никакой структуры — поток событий.
- **Никогда не повредим прошлые данные.** Мы только дописываем. Старые байты не трогаем. Если новая запись не дописалась до конца (упали в момент записи) — она просто отбросится при восстановлении как невалидная.

### Какая структура у одной WAL-записи

В реальных БД — бинарный формат с длиной, типом операции, контрольной суммой (CRC), LSN (log sequence number). В лабораторной я взял JSON-lines: одна операция на строку.

```
{"op": "set", "k": "user:1", "v": "Alice"}
{"op": "set", "k": "user:2", "v": "Bob"}
{"op": "del", "k": "user:1"}
{"op": "set", "k": "user:2", "v": "Bobby"}
```

Преимущества JSON:
- Читается глазами — удобно отлаживать.
- Кросс-платформенно.
- Тривиально парсить.

Недостатки:
- В разы больше по размеру, чем бинарный формат.
- Парсинг медленнее.
- Нет контрольных сумм — повреждение середины строки сделает её невалидной (JSON не распарсится), и мы её просто отбросим. Для лабы это нормально.

## 3. Гарантии записи и зачем `fsync`

Запись на диск — это не одно действие, а каскад:

1. `f.write(...)` — Python кладёт байты в буфер библиотеки IO.
2. `f.flush()` — буфер библиотеки сбрасывается в буфер ядра ОС (page cache).
3. **`os.fsync(fd)`** — ОС физически записывает page cache на устройство и просит устройство подтвердить.
4. Устройство пишет в свой внутренний кеш, потом — на пластины/во флеш-память.

Если процесс упал между шагами 1–2 — потеря данных гарантирована, ничего ещё не дошло до ОС.
Если ОС упала (kernel panic, питание) между шагами 2–3 — данные пропадут вместе с page cache, потому что ОС обещала записать, но не успела.
Только после `fsync` мы можем считать, что данные точно на диске.

Поэтому в коде:
```python
with open(self._wal_path, "a", encoding="utf-8") as f:
    f.write(line)
    f.flush()
    os.fsync(f.fileno())
```

Цена: `fsync` — медленная операция (на HDD — миллисекунды, на SSD — десятки/сотни микросекунд), потому что ждёт реального устройства. Высоконагруженные БД её группируют («батчат»): один `fsync` подтверждает сразу пачку операций, амортизируя цену. У нас в лабе делаем по `fsync` на каждую операцию — это самый строгий режим (durability на каждой записи).

### Порядок «WAL → память»

```python
def set(self, k, v):
    ...
    self._append_wal({"op": "set", "k": k, "v": v})   # 1. сначала на диск
    with self._lock:
        self._store[k] = v                             # 2. потом в память
```

Что будет, если поменять местами?
- Сначала память, потом WAL: если упадём между — клиент мог бы прочитать значение из памяти и подумать «оно сохранено», но на диске его нет. После рестарта значение пропало → клиент видел призрак. Это нарушение durability.
- Сначала WAL, потом память (как у нас): если упадём между — операция в журнале есть, при восстановлении она применится. Клиент в этот момент ещё не получил «ОК», потому что метод не вернулся. Корректно.

Это и называется **write-ahead**.

## 4. Recovery: восстановление состояния

В `__init__` кэша мы открываем WAL и проигрываем его «как пластинку»:

```python
def _replay(self):
    with open(self._wal_path, "r", encoding="utf-8") as f:
        for line in f:
            rec = json.loads(line.strip())
            op = rec.get("op")
            k = rec.get("k")
            if op == "set":
                self._store[k] = rec.get("v")
            elif op == "del":
                self._store.pop(k, None)
```

Важно: применяем операции в **том же порядке**, в котором они были записаны. Тогда конечное состояние памяти будет идентичным тому, что было перед падением (за вычетом операций, которые не успели сделать `fsync`).

Один тонкий момент — обработка испорченных строк:
```python
try:
    rec = json.loads(line)
except json.JSONDecodeError:
    continue
```
Если процесс упал прямо в момент записи, последняя строка может быть оборвана. Мы её просто пропускаем (правильное поведение: «эта операция не подтверждена, считаем что её не было»).

### Идемпотентность

Recovery должно быть **идемпотентным**: проиграть WAL дважды должно дать тот же результат, что и проиграть один раз. У нас это естественно: операции `set k v` и `del k` повторяемы без побочных эффектов. Это упрощает обработку всяких сложных сценариев (двойные старты, чтение во время компактизации и т.д.).

## 5. Компактизация и зачем она

Беда append-only журнала: **он растёт бесконечно**.

Пример: счётчик просмотров инкрементируется миллион раз → миллион строк в WAL. Хотя текущее состояние — одна пара `views = 1000000`.

Последствия:
- **Долгий старт.** Чтобы восстановиться, надо прочитать миллион строк и применить миллион операций.
- **Дисковое пространство.** Миллион JSON-строк по 50 байт — это 50 МБ ради одного целого числа.

Решение: **компактизация (compaction)** — периодически делаем «снимок» текущего состояния и заменяем им длинный лог.

Алгоритм:
1. Берём snapshot текущего in-memory словаря.
2. Пишем во **временный** файл `wal.compact` минимальный набор операций, который восстановит этот snapshot — по одному `set` на каждую живую запись.
3. Гарантируем, что временный файл реально на диске (`fsync`).
4. Атомарно подменяем им оригинальный WAL.

После этого:
- Размер WAL = размер «живого» состояния (без истории).
- Восстановление становится быстрым: N записей вместо миллиона.

### Условия безопасности

- Snapshot нужно брать под общей блокировкой кэша. Иначе пока мы итерируем словарь, кто-то его меняет — получим `RuntimeError` или несогласованное состояние.
- Во время компактизации не должны теряться **параллельные новые записи**. У нас простое решение: `_wal_lock` блокирует и `_append_wal`, и `compact`. Это значит, что во время компактизации `set`/`delete` встанут на паузу. В реальных БД делают сложнее: пишут компактизацию в новый файл, параллельно фиксируя новые операции в дополнительный лог, потом сливают. Для учебной задачи достаточно простой блокировки.

### Раз в минуту — фоновый поток

```python
self._compactor = threading.Thread(target=self._compaction_loop, daemon=True)
```
Поток с тем же паттерном, что в лабе 2: `Event.wait(interval)` крутится, по таймауту дёргает `compact()`. По требованию задания — раз в минуту.

## 6. Атомарная подмена файла

Магическая строка:
```python
os.replace(tmp_path, self._wal_path)
```

`os.replace` — это переименование с гарантией атомарности на POSIX-системах (на Windows тоже работает с теми же гарантиями). «Атомарно» значит: с точки зрения любого другого процесса, открывающего этот путь, в любой момент времени по нему лежит либо **старый** файл, либо **новый** — никаких промежуточных состояний (полусобранный файл, пустой файл).

Почему это критично. Альтернатива: открыть оригинальный WAL на запись, перезаписать его содержимое снапшотом. Если упадём посередине:
- старый WAL уже частично затёрт;
- новый ещё не дописан;
- recovery не сможет восстановить состояние.

С шаблоном «временный файл + rename» мы защищены: либо упали до `replace` — оригинальный WAL цел, временный недописан, его можно просто удалить и попробовать ещё раз; либо упали после `replace` — на месте уже новый корректный WAL.

Это универсальный паттерн «atomic file write», его используют везде, где нужно безопасно подменить файл (конфиги, кеши, дампы состояния).

## 7. Разбор кода `wal_cache.py`

Файл: [wal_cache.py](wal_cache.py).

### Инициализация

```python
def __init__(self, wal_path: str, compaction_interval: float = 60.0):
    self._wal_path = wal_path
    self._store: dict[Any, Any] = {}
    self._lock = threading.RLock()
    self._wal_lock = threading.Lock()
```

Две блокировки специально:
- `_lock` — защищает in-memory словарь, нужна на быстрых операциях.
- `_wal_lock` — сериализует **запись в файл** (`_append_wal`) и компактизацию. Файловые операции медленные (`fsync` — миллисекунды), не хочется блокировать ими чтения из памяти. Поэтому `get` берёт только `_lock`, а WAL-запись — отдельный мьютекс.

```python
os.makedirs(os.path.dirname(os.path.abspath(wal_path)) or ".", exist_ok=True)
if not os.path.exists(wal_path):
    open(wal_path, "a").close()
else:
    self._replay()
```
- Создаём родительский каталог, если его нет (`exist_ok=True` — не ругаться, если уже есть).
- Если WAL отсутствует — создаём пустой (`open(..., "a")` создаёт, если нет).
- Если есть — прокручиваем `_replay()`.

Это точно соответствует заданию: «При создании и инициализации кэша он читает файл WAL (если он есть на файловой системе, если нет, то создает его)».

### `_append_wal`

```python
def _append_wal(self, record: dict) -> None:
    line = json.dumps(record, ensure_ascii=False) + "\n"
    with self._wal_lock:
        with open(self._wal_path, "a", encoding="utf-8") as f:
            f.write(line)
            f.flush()
            os.fsync(f.fileno())
```
- Открываем файл в режиме `"a"` (append) — указатель сразу в конце, новые байты гарантированно дописываются.
- `flush()` + `fsync()` — обсуждали выше, гарантия durability.
- Файл открывается-закрывается на каждой записи. Цена — небольшой оверхед, выгода — нет постоянно открытого дескриптора. В продакшен-системах держат файл открытым; для лабы простота важнее.
- `ensure_ascii=False` — не экранировать не-ASCII символы (`{"k": "Алиса"}` пишется как есть, а не `{"k": "А..."}`).

### `set`, `get`, `delete`

`set` и `delete` — сначала `_append_wal`, потом изменение `_store` под `_lock`. `get` — только под `_lock`, в файл не пишет (чтение не меняет состояния).

### `compact`

```python
def compact(self) -> None:
    tmp_path = self._wal_path + ".compact"
    with self._wal_lock:
        with self._lock:
            snapshot = list(self._store.items())
        with open(tmp_path, "w", encoding="utf-8") as f:
            for k, v in snapshot:
                f.write(json.dumps({"op": "set", "k": k, "v": v}, ensure_ascii=False) + "\n")
            f.flush()
            os.fsync(f.fileno())
        os.replace(tmp_path, self._wal_path)
```

Порядок блокировок:
1. Берём `_wal_lock` (пока компактимся, никто другой не пишет в файл).
2. Внутри берём `_lock` ровно на копирование snapshot — быстро отпускаем, чтобы не блокировать `get` дольше нужного.
3. Долгую часть (пишем файл + fsync) делаем без `_lock` — `get` может работать.

### `close`

```python
def close(self):
    self._stop_event.set()
    self._compactor.join(timeout=1.0)
```
Поднимаем флаг остановки, ждём, пока поток-компактор закончит текущую итерацию и выйдет. Файлы открываются-закрываются по требованию — отдельного `close` для дескрипторов не нужно.
