## 1. Что такое кэш и зачем он нужен

**Кэш** — структура «ключ → значение» в оперативной памяти, к которой обращаются вместо медленного источника (диск, сеть, БД).

Жизненный пример: пользователь зашёл в приложение, мы достали его профиль из БД (50 мс) и положили в кэш под ключ `user:42`. В следующие 100 запросов отдаём из памяти (0.01 мс). Это и есть смысл кэша — обменять оперативку на скорость.

С точки зрения интерфейса кэш почти неотличим от обычного `dict`:
```python
cache.set("user:42", profile)
cache.get("user:42")
cache.delete("user:42")
```

Но у настоящего кэша есть три вещи, которых нет у `dict`:
1. **TTL** — записи самоуничтожаются по таймеру.
2. **Потокобезопасность** — несколько потоков могут безопасно работать одновременно.
3. **Атомарные read-modify-write операции** — типа «инкрементируй счётчик» без гонок.

Эти три пункта и есть содержание лабы.

## 2. TTL — срок жизни ключа

**TTL (Time To Live)** — время в секундах, через которое запись должна перестать существовать. Это нужно по двум причинам:

- **Гигиена памяти.** Без TTL кэш разрастается до бесконечности. Если положили 10 миллионов токенов сессий и никто их не удалил — процесс упадёт по OOM.
- **Свежесть данных.** Кэш — это копия. Оригинал может измениться, а кэш — нет. TTL ограничивает рассинхронизацию: «не более чем на 60 секунд устаревший».

### Как технически реализовать TTL

Есть два подхода:

**Ленивая проверка (lazy expiration).** При каждом `get` смотрим: время записи + TTL уже прошло? Если да — возвращаем `None` и удаляем. Минусы: если ключ больше никто никогда не запросит, он будет висеть в памяти вечно.

**Активная чистка фоновым потоком.** Отдельный поток просыпается каждые N секунд и удаляет всё, что протухло. Минусы: чуть больше сложности (поток + блокировка), и удаление может произойти не точно в момент истечения, а чуть позже (на интервал чистки).

**Задание прямо требует второй вариант:** «использовать поток, который следит за истечением времени хранения ключа». У нас реализованы оба — фоновая чистка + защита внутри `get`/`compute_if_present` на случай, если читают раньше, чем поток отработал.

### Почему `time.monotonic()`, а не `time.time()`

`time.time()` — это «настенные часы», их можно перевести (вручную, через NTP, перевод DST). Если мы сохраним «истекает в 12:00:30», а пользователь переведёт часы назад на час, ключ проживёт лишний час.

`time.monotonic()` — это «секундомер от запуска процесса». Он только растёт и никогда не прыгает. Для любых таймаутов, дедлайнов, таймеров — только `monotonic`.

## 3. Потоки и почему без блокировок данные ломаются

**Поток (thread)** — параллельная линия исполнения внутри одного процесса. У них общая память, но операционная система может в любой момент переключиться с одного потока на другой.

### Что такое race condition

Race condition (гонка данных) — это ситуация, когда результат зависит от того, в каком порядке потоки успеют выполнить свои операции.

Простой пример. Пусть в памяти `counter = 5`. Два потока А и Б одновременно делают `counter += 1`. На уровне процессора эта операция — не одно действие, а три:

```
1. LOAD  counter в регистр    (читаем 5)
2. ADD   регистр + 1           (получили 6)
3. STORE регистр в counter     (записали 6)
```

Возможный сценарий:
```
поток А: LOAD  → R1 = 5
поток Б: LOAD  → R2 = 5     ← переключение тут
поток А: ADD   → R1 = 6
поток А: STORE → counter = 6
поток Б: ADD   → R2 = 6
поток Б: STORE → counter = 6
```

Сделали два инкремента, а получили один. **Один из инкрементов «потерялся».**

### Блокировки (locks/mutexes)

Решение — обозначить участок кода, в котором одновременно может быть только один поток. Это делает **мьютекс** (mutual exclusion):

```python
lock = threading.Lock()

with lock:
    counter += 1   # пока мы тут — никто другой сюда не зайдёт
```

Все остальные потоки, попытавшись войти в `with lock:`, заблокируются (приостановятся) и будут ждать, пока текущий из него выйдет. Внутри блока опасной гонки нет — поток исполняется монопольно.

### `Lock` vs `RLock

В коде я использовал `threading.RLock()` — «реентерабельный» мьютекс. Отличие:
- Обычный `Lock`: если один и тот же поток попытается захватить мьютекс дважды подряд (например, метод А под `with lock:` вызвал метод Б, который тоже хочет `with lock:`) — будет deadlock, поток встанет навечно сам себя ждать.
- `RLock`: тот же поток может захватить столько раз, сколько хочет, лишь бы столько же раз освободил.

`RLock` чуть медленнее, но безопаснее при вложенных вызовах. Для учебной задачи разница пренебрежима, зато код устойчив к рефакторингу.

### Глобальная блокировка интерпретатора (GIL) — а нужно ли вообще

В CPython есть **GIL** — глобальный мьютекс, который не даёт двум потокам Python исполнять байткод одновременно. Возникает резонный вопрос: «раз есть GIL, может, и блокировки наши не нужны?»

Нужны. GIL гарантирует атомарность **одной байткод-инструкции**, но `counter += 1` — это **несколько** инструкций (`LOAD_FAST`, `LOAD_CONST`, `BINARY_ADD`, `STORE_FAST`). GIL может переключить поток между ними. Поэтому блокировки нужны на любую составную операцию: чтение-модификация-запись, проверка-и-вставка и т.д.

## 4. Атомарные операции и `compute_if_present`

`compute_if_present(k, func)` — это атомарный паттерн «прочитать значение, применить функцию, записать обратно». В Java такая штука есть на `ConcurrentHashMap`, в Go её собирают вручную, в Redis — через транзакции (`MULTI/EXEC`) или Lua-скрипты.

Зачем атомарность. Допустим, мы хотим инкрементировать счётчик в кэше:
```python
v = cache.get('counter')         # читаем (например, 5)
cache.set('counter', v + 1)      # записываем 6
```
Между `get` и `set` другой поток может тоже сделать `get` → получит 5, посчитает 6, перезапишет нашу запись. Инкремент потеряется.

Правильно — отдать обе операции внутрь кэша одной командой:
```python
cache.compute_if_present('counter', lambda v: v + 1)
```
Кэш под своей блокировкой делает чтение, вызов функции, запись — никто другой в это время не вмешается.

В коде это буквально:
```python
def compute_if_present(self, k, func):
    with self._lock:
        if k not in self._store: return None
        new_value = func(self._store[k])
        self._store[k] = new_value
        return new_value
```

Проверка из задания: три потока × 1000 итераций инкремента. Если реализация правильная — счётчик ровно 3000. Если бы мы делали `get` + `set` снаружи без атомарности — получили бы число существенно меньше (обычно 1500–2800 в зависимости от того, как лягут переключения).

⚠️ Важный нюанс: функция, передаваемая в `compute_if_present`, исполняется **под блокировкой кэша**. Поэтому:
- Она должна быть **быстрой** (никаких сетевых вызовов, IO, тяжёлых вычислений).
- Она не должна **рекурсивно вызывать** методы того же кэша. С `RLock` это не зависнет, но логика становится непредсказуемой.

## 5. Разбор кода `cache.py` построчно

Файл: [cache.py](cache.py).

### Инициализация

```python
def __init__(self, cleanup_interval: float = 0.1):
    self._store: dict[Any, Any] = {}
    self._expirations: dict[Any, float] = {}
    self._lock = threading.RLock()
    self._cleanup_interval = cleanup_interval
    self._stop_event = threading.Event()
    self._cleaner = threading.Thread(target=self._cleanup_loop, daemon=True)
    self._cleaner.start()
```

- `_store` — основное хранилище, `ключ → значение`.
- `_expirations` — параллельный словарь, `ключ → момент истечения` (в секундах `time.monotonic()`). Хранится отдельно, потому что у ключей без TTL записи в `_expirations` просто нет — экономим место.
- `_lock` — `RLock`, защищает оба словаря.
- `_stop_event` — `threading.Event` это «флажок», на котором можно ждать. У него есть метод `wait(timeout)` — ждёт либо до timeout, либо пока кто-то не вызовет `.set()` (флажок поднят). Удобный способ останавливать фоновые потоки без `time.sleep`, который не прерывается.
- `_cleaner` — фоновый поток-чистильщик. `daemon=True` означает, что когда основной поток (программа) завершится, питон не будет ждать этот поток — он умрёт вместе с процессом. Без этого программа не сможет нормально выйти, пока поток крутится.

### Цикл чистки

```python
def _cleanup_loop(self):
    while not self._stop_event.wait(self._cleanup_interval):
        now = time.monotonic()
        with self._lock:
            expired = [k for k, exp in self._expirations.items() if exp <= now]
            for k in expired:
                self._store.pop(k, None)
                self._expirations.pop(k, None)
```

Логика `while not self._stop_event.wait(interval):` — это «крутимся, пока никто не сказал стоп»:
- `wait(interval)` возвращает `True`, если флажок был поднят (значит, нас просят выйти) — выходим из цикла.
- Возвращает `False` по таймауту → значит, прошёл `interval` секунд, пора чистить.

Под блокировкой:
1. Собираем список протухших ключей.
2. Удаляем их из обоих словарей.

Почему два прохода (сначала список, потом удаление): нельзя модифицировать словарь во время итерации по нему — питон бросит `RuntimeError`. Сначала собрали — потом удалили.

### `set`

```python
def set(self, k, v, ttl=None):
    if k is None:
        raise ValueError("key must not be None")
    with self._lock:
        self._store[k] = v
        if ttl is not None:
            self._expirations[k] = time.monotonic() + ttl
        else:
            self._expirations.pop(k, None)
```

Нюанс: если ключ был с TTL, а мы заново его положили без TTL — нужно стереть старую запись из `_expirations`. Иначе он бы внезапно протух по старому таймеру, хотя пользователь явно сказал «без TTL».

### `get`

```python
def get(self, k):
    if k is None:
        raise ValueError("key must not be None")
    with self._lock:
        exp = self._expirations.get(k)
        if exp is not None and exp <= time.monotonic():
            self._store.pop(k, None)
            self._expirations.pop(k, None)
            return None
        return self._store.get(k)
```

Ленивая проверка истечения здесь нужна для случая «фоновый поток ещё не успел почистить, а пользователь уже спрашивает». Просыпается раз в 100 мс, между просыпаниями ключ формально протух — мы не должны его отдавать. Без этой проверки можно было бы получить уже мёртвое значение.

### `delete`

```python
def delete(self, k):
    if k is None:
        raise ValueError("key must not be None")
    with self._lock:
        self._expirations.pop(k, None)
        return self._store.pop(k, None)
```

`dict.pop(k, None)` — удалить и вернуть значение, или вернуть `None`, если ключа не было. Никаких исключений.

### `compute_if_present`

Подробно разобран в разделе 4. Здесь ещё раз обращаю внимание на проверку истечения — она нужна, чтобы не вызвать `func` на протухшем значении.

### `close` и `__del__`

```python
def close(self):
    self._stop_event.set()
    self._cleaner.join(timeout=1.0)
```

`set()` на Event поднимает флажок → следующий `wait()` в цикле сразу вернёт `True` → цикл выйдет. `join(timeout)` ждёт, пока поток реально завершится, но не дольше указанного. Это вежливое завершение фоновой работы.

`__del__` — деструктор, питон вызывает его при сборке мусора. Полагаться на него не стоит (момент вызова непредсказуем), но как страховка от утечки потоков — пригодится.

## 6. Тесты в `main.ipynb` — что проверяем и почему

Файл: [main.ipynb](main.ipynb).

### Базовые операции
Простой sanity check: `set` положил, `get` достал, `delete` удалил, `get` после `delete` вернул `None`.

### Запрет `None` как ключа
Задание: «Ключ не должен быть null». Проверяем, что все три метода (`set`, `get`, `delete`) на `None` бросают `ValueError`. Без этого можно было бы случайно положить `None` как ключ и не понять, почему «ничего не работает».

### TTL и фоновая чистка
Кладём ключ с TTL=1 секунда, читаем через 0.5 с (должен быть), через 1.3 с (не должно быть). Дополнительно проверяем `'temp' in cache._store` — это подтверждает, что фоновый поток **физически удалил** запись из внутреннего хранилища, а не просто что `get` вернул `None` по ленивой проверке. Этим мы доказываем, что поток работает.

### `compute_if_present` базовый
Без многопоточности: на существующем ключе функция применяется, значение обновляется; на несуществующем — возвращается `None` и функция не вызывается.

### Потокобезопасность — главный тест
```python
cache.set('counter', 0)

def worker():
    for _ in range(1000):
        cache.compute_if_present('counter', lambda v: v + 1)

threads = [threading.Thread(target=worker) for _ in range(3)]
for t in threads: t.start()
for t in threads: t.join()

assert cache.get('counter') == 3000
```

Это сценарий из задания. Если бы атомарности в `compute_if_present` не было — на любом запуске мы бы получили число меньше 3000 и `assert` бы упал. Любой запуск с правильной реализацией даёт ровно 3000.
