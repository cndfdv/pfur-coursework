# Теория для сдачи лабораторных 3-7

## Лаба 3: исключения, файлы, слоистая архитектура

Что нужно уметь объяснить:

- `try/except` нужен не для скрытия ошибок, а для контролируемой реакции на ожидаемые сбои.
- `Fatal error` останавливает программу: например, нет входной директории.
- `Domain error` означает нарушение бизнес-правил: сумма транзакции меньше или равна нулю.
- `Graceful degradation` означает, что один битый файл или строка не валит всю обработку.
- `Fail fast` означает, что опасные состояния лучше останавливать сразу.

Архитектура:

- `app/io` читает данные с диска.
- `app/services/validator.py` проверяет бизнес-правила.
- `app/services/aggregator.py` считает итоговые суммы.
- `app/core` хранит модели и кастомные исключения.

Почему это важно: если завтра добавят XML, нужно добавить reader и регистрацию расширения, а не переписывать всю программу.

## Лаба 4: тестирование

Пирамида тестов:

- Unit-тесты проверяют одну функцию: например, `validate`.
- Integration-тесты проверяют связку модулей: чтение файла, валидация, агрегация.
- E2E-тесты проверяют программу целиком от входных файлов до `result.json`.

Паттерн AAA:

- Arrange: подготовили входные данные.
- Act: вызвали функцию.
- Assert: проверили результат.

`tmp_path` нужен, чтобы тесты создавали временные файлы и не пачкали проект. `parametrize` нужен, чтобы одним тестом проверить много входных значений. `mock/patch` нужен, чтобы имитировать системные сбои, например ошибку записи на диск.

## Лаба 5: ленивые вычисления и большие файлы

Главная идея: нельзя делать `readlines()` или хранить все транзакции в списке, если файл может быть большим.

Нужно объяснить:

- Итератор отдаёт элементы по одному через `__next__`.
- Генератор — функция с `yield`; она сохраняет состояние между вызовами.
- Pipeline — цепочка генераторов: чтение -> парсинг -> валидация -> агрегация.
- Память должна зависеть не от числа строк, а от числа категорий.

В этой работе `aggregate_by_category` хранит только словарь сумм по категориям. Это O(K) по памяти, где K — количество категорий.

`tracemalloc` показывает текущее и пиковое потребление памяти. Им доказывают, что обработка файла большого размера не раздувает RAM линейно.

## Лаба 6: асинхронное программирование

Синхронный код ждёт каждый запрос полностью и только потом начинает следующий. Это плохо для I/O-bound задач, где программа в основном ждёт сеть.

Асинхронность:

- `async def` создаёт корутину.
- `await` отдаёт управление event loop, пока операция ждёт I/O.
- `asyncio.gather` запускает много корутин конкурентно.
- `aiohttp.ClientSession` переиспользует соединения.
- `asyncio.Semaphore` ограничивает количество одновременных запросов.
- `ClientTimeout` защищает от вечного ожидания.

Важно: внутри `async def` нельзя использовать блокирующие вызовы вроде `requests.get()` или `time.sleep()`, иначе блокируется весь event loop.

Асинхронность не равна параллелизму. Она обычно работает в одном потоке, но эффективно переключается между задачами ожидания.

## Лаба 7: Git

Минимум для сдачи тренажёра:

- `commit` фиксирует состояние проекта.
- `branch` создаёт отдельную ветку разработки.
- `checkout` или `switch` переключает ветки.
- `merge` объединяет ветки, создавая merge commit при необходимости.
- `rebase` переносит коммиты поверх другой базы и делает историю линейной.
- `HEAD` указывает на текущий коммит.
- `^` означает родительский коммит, например `HEAD^`.
- `~3` означает на три коммита назад, например `HEAD~3`.
- `cherry-pick` переносит выбранный коммит в текущую ветку.
- `clone` копирует удалённый репозиторий.
- `fetch` скачивает изменения без слияния.
- `pull` это `fetch` плюс интеграция изменений.
- `push` отправляет локальные коммиты на remote.

На вопрос про разницу `merge` и `rebase`: `merge` сохраняет реальную историю ветвления, `rebase` переписывает базу коммитов и делает историю ровнее. Публичные общие ветки без необходимости лучше не ребейзить.
