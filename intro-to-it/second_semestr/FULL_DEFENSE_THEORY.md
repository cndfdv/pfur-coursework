# Лабораторная 1: культура кода, типизация, анализ текста

## Суть лабораторной

В первой лабораторной нужно было написать простую функцию анализа текста. На первый взгляд задача маленькая, но главная цель не в самом подсчёте слов, а в привыкании к инженерному стилю:

- писать код в `.py` файле, а не только в ноутбуке;
- оформлять код по PEP 8;
- добавлять type hints;
- писать docstring;
- делать функцию с понятным входом и выходом.

В проекте это файл:

```text
second_semestr/lab_1/text_analyzer.py
```

Главная функция:

```python
def analyze_text(text: str) -> dict[str, Union[int, float]]:
```

Она принимает строку и возвращает словарь со статистикой.

## PEP 8

PEP 8 — это официальный стиль оформления Python-кода. Он описывает, как называть переменные, как ставить отступы, где оставлять пустые строки, какой длины должны быть строки и так далее.

Главная идея PEP 8: код чаще читают, чем пишут. Если каждый пишет как хочет, проект быстро становится трудно поддерживать.

Примеры правил:

- отступы по 4 пробела;
- имена функций и переменных в `snake_case`;
- имена классов в `CamelCase`;
- пробелы вокруг операторов: `a + b`, а не `a+b`;
- понятные имена вместо `x`, `tmp`, `data1`, если смысл не очевиден.

Что сказать на защите:

PEP 8 нужен не для работы интерпретатора, а для людей. Код будет выполняться и без PEP 8, но его будет сложнее читать, проверять и поддерживать.

## Линтер

Линтер — это инструмент, который автоматически проверяет стиль кода и некоторые потенциальные ошибки.

Пример: `flake8`.

Он может заметить:

- слишком длинную строку;
- неиспользуемый импорт;
- неправильные отступы;
- лишние пробелы;
- нарушения PEP 8.

Важно понимать: линтер не доказывает, что программа работает правильно. Он проверяет качество оформления и часть статических ошибок.

## Type hints

Type hints — это аннотации типов. Они показывают, какие типы данных функция ожидает и что возвращает.

Пример:

```python
def analyze_text(text: str) -> dict[str, int | float]:
    ...
```

Здесь видно:

- `text: str` — функция ждёт строку;
- `-> dict[...]` — функция возвращает словарь.

Python остаётся динамическим языком. Это значит, что во время выполнения Python сам не запрещает передать неправильный тип, если специально не включать проверку через сторонние инструменты.

Зачем тогда нужны type hints:

- IDE показывает подсказки;
- `mypy` может проверить типы до запуска;
- другому человеку проще понять код;
- проще поддерживать большой проект;
- меньше случайных ошибок при изменениях.

Что сказать на защите:

Type hints — это документация для человека и инструментов. Они не делают Python статически типизированным автоматически, но помогают находить ошибки раньше.

## Docstring

Docstring — это строка документации внутри функции, класса или модуля.

Пример:

```python
def analyze_text(text: str) -> dict:
    """Анализирует текст и возвращает статистику."""
```

Docstring должен отвечать на вопросы:

- что делает функция;
- какие аргументы принимает;
- что возвращает;
- какие ошибки может вызвать, если это важно.

Отличие docstring от обычного комментария:

- docstring является частью объекта и доступен через `help()` или `.__doc__`;
- комментарий просто игнорируется интерпретатором.

## Как работает анализ текста

Функция делает несколько шагов.

### 1. Приведение к нижнему регистру

```python
text = text.lower()
```

Это нужно, чтобы слова `Hello`, `hello` и `HELLO` считались одним словом.

Без этого уникальные слова считались бы неправильно:

```text
Hello hello
```

Без `lower()` здесь было бы 2 уникальных слова, хотя по смыслу это одно слово.

### 2. Удаление пунктуации

```python
text = text.translate(str.maketrans("", "", string.punctuation))
```

`string.punctuation` содержит стандартные знаки пунктуации: точки, запятые, восклицательные знаки и так далее.

`str.maketrans("", "", chars)` создаёт таблицу перевода, где третий аргумент означает символы, которые надо удалить.

Зачем это нужно:

```text
hello
hello!
hello,
```

Без удаления пунктуации это были бы разные строки. После удаления пунктуации все станут `hello`.

### 3. Разбиение на слова

```python
words = text.split()
```

`split()` без аргументов разбивает строку по любым пробельным символам:

- пробел;
- табуляция;
- перевод строки;
- несколько пробелов подряд.

Это удобнее, чем `split(" ")`, потому что `split(" ")` хуже работает с несколькими пробелами подряд.

### 4. Подсчёт общего количества слов

```python
total_words = len(words)
```

Это просто длина списка слов.

### 5. Подсчёт уникальных слов

```python
unique_words = len(set(words))
```

`set` — множество. Оно хранит только уникальные элементы.

Пример:

```python
set(["a", "b", "a"])
```

Результат:

```python
{"a", "b"}
```

Поэтому `len(set(words))` даёт количество уникальных слов.

### 6. Средняя длина слова

```python
avg_word_length = round(sum(len(w) for w in words) / total_words, 2)
```

Здесь:

- `len(w)` — длина одного слова;
- `sum(...)` — сумма длин всех слов;
- деление на `total_words` — средняя длина;
- `round(..., 2)` — округление до двух знаков.

## Важный крайний случай

Если передать пустую строку, список слов будет пустой:

```python
words = []
total_words = 0
```

Тогда средняя длина вызовет деление на ноль. Это слабое место реализации.

Если преподаватель спросит:

Вопрос: что будет на пустой строке?

Ответ: в текущей реализации будет ошибка деления на ноль. Правильное улучшение — отдельно обработать случай `total_words == 0` и вернуть нули.

Пример улучшения:

```python
if total_words == 0:
    return {
        "total_words": 0,
        "unique_words": 0,
        "avg_word_length": 0.0,
    }
```

## Частые вопросы по лабе 1

Вопрос: зачем нужен `set`?

Ответ: чтобы убрать повторы и посчитать уникальные слова.

Вопрос: чем `split()` отличается от `split(" ")`?

Ответ: `split()` разбивает по любым пробельным символам и игнорирует лишние пробелы. `split(" ")` разбивает только по обычному пробелу и может давать пустые строки.

Вопрос: почему используется `string.punctuation`?

Ответ: чтобы не перечислять знаки пунктуации вручную.

Вопрос: типизация обязательна для выполнения Python-кода?

Ответ: нет, но она помогает инструментам и людям понимать ожидаемые типы.

# Лабораторная 2: ООП и математический вектор

## Суть лабораторной

Во второй лабораторной нужно было реализовать собственный класс `Vector`.

Файл:

```text
second_semestr/lab_2/vector_math.py
```

Класс умеет:

- хранить координаты;
- красиво выводиться;
- складываться с другим вектором;
- умножаться на число;
- умножаться на другой вектор через скалярное произведение;
- считать евклидову норму.

Главная цель лабораторной — понять основы ООП и магические методы.

## Что такое ООП

ООП — объектно-ориентированное программирование. Его идея: объединить данные и поведение в одну сущность.

Например, вектор — это не просто tuple координат. У него есть:

- данные: координаты;
- поведение: сложение, умножение, вычисление длины.

Поэтому удобно оформить его как класс.

## Класс и объект

Класс — это шаблон.

Объект — конкретный экземпляр класса.

Пример:

```python
class Vector:
    ...

v = Vector(1, 2, 3)
```

`Vector` — класс.

`v` — объект.

Можно создать много объектов одного класса:

```python
a = Vector(1, 2)
b = Vector(3, 4)
```

У них одинаковое поведение, но разные координаты.

## Атрибуты и методы

Атрибуты — данные объекта.

В этой лабораторной:

```python
self.coords = tuple(args)
```

`coords` — атрибут.

Методы — функции внутри класса:

- `__add__`;
- `__mul__`;
- `norm`.

Они работают с данными объекта.

## Что такое `self`

`self` — ссылка на текущий объект.

Когда мы вызываем:

```python
v.norm
```

Python внутри передаёт объект `v` в метод как `self`.

Если есть:

```python
a = Vector(1, 2)
b = Vector(3, 4)
```

то внутри методов `self` позволяет понять, с каким именно объектом сейчас работаем.

## `__init__`

`__init__` — метод инициализации объекта. Он вызывается после создания объекта.

В лабораторной:

```python
def __init__(self, *args: Union[int, float]) -> None:
    self.coords = tuple(args)
```

Когда пишем:

```python
Vector(1, 2, 3)
```

значения `1, 2, 3` попадают в `*args`.

## Зачем `*args`

`*args` позволяет принять любое количество позиционных аргументов.

Это удобно для N-мерного вектора:

```python
Vector(1, 2)
Vector(1, 2, 3)
Vector(1, 2, 3, 4, 5)
```

Если бы мы написали только `x, y`, класс поддерживал бы только двумерные векторы.

## Почему координаты хранятся в tuple

`tuple` — неизменяемая структура данных.

Для математического вектора это нормально: операции обычно не меняют старый вектор, а возвращают новый.

Например:

```python
c = a + b
```

Ожидается, что `a` и `b` останутся прежними, а результат будет в `c`.

Это делает поведение более предсказуемым.

## Магические методы

Магические методы, или dunder methods, начинаются и заканчиваются двойным подчёркиванием:

```python
__init__
__repr__
__add__
__mul__
```

Python вызывает их автоматически в определённых ситуациях.

Например:

```python
a + b
```

на самом деле вызывает:

```python
a.__add__(b)
```

А:

```python
a * b
```

вызывает:

```python
a.__mul__(b)
```

## `__repr__`

`__repr__` отвечает за строковое представление объекта.

В лабораторной результат выглядит так:

```text
Vector(1, 2, 3)
```

Это полезно для отладки: когда печатаем объект, видим его координаты.

Разница между `__str__` и `__repr__`:

- `__str__` — более человекочитаемый вывод;
- `__repr__` — более точный вывод для разработчика.

Если `__str__` не определён, `print()` может использовать `__repr__`.

## Сложение векторов

Сложение выполняется покомпонентно:

```text
(1, 2, 3) + (4, 5, 6) = (5, 7, 9)
```

В коде это делается через `zip`:

```python
tuple(a + b for a, b in zip(self.coords, other.coords))
```

`zip` берёт пары элементов:

```text
(1, 4), (2, 5), (3, 6)
```

Почему надо проверять размерность:

```text
(1, 2, 3) + (4, 5)
```

У третьей координаты первого вектора нет пары. Математически такая операция некорректна.

Поэтому выбрасывается:

```python
ValueError("Векторы разной размерности")
```

## Умножение на число

Если вектор умножается на число, каждая координата умножается на это число:

```text
(1, 2, 3) * 10 = (10, 20, 30)
```

Результат — новый `Vector`.

## Скалярное произведение

Если вектор умножается на другой вектор, результат — число:

```text
(1, 2, 3) * (4, 5, 6) = 1*4 + 2*5 + 3*6 = 32
```

Это называется скалярное произведение.

Для него тоже нужна одинаковая размерность.

## `isinstance`

`isinstance` проверяет тип объекта.

В `__mul__` надо понять, что пришло справа:

- число;
- другой вектор;
- что-то неподдерживаемое.

Если тип неподдерживаемый, выбрасывается `TypeError`.

## `@property`

`@property` превращает метод в вычисляемое свойство.

Вместо:

```python
v.norm()
```

пишем:

```python
v.norm
```

Почему это логично: длина вектора выглядит как характеристика объекта, а не как действие.

## Евклидова норма

Евклидова норма — длина вектора.

Для двумерного вектора:

```text
(3, 4)
```

длина:

```text
sqrt(3^2 + 4^2) = 5
```

Для N-мерного:

```text
sqrt(x1^2 + x2^2 + ... + xn^2)
```

## Частые вопросы по лабе 2

Вопрос: почему операции возвращают новый вектор, а не меняют старый?

Ответ: так математические объекты ведут себя предсказуемее. `a + b` должен дать результат, но не менять `a` и `b`.

Вопрос: зачем нужен `__mul__`, если можно сделать обычный метод?

Ответ: магический метод позволяет использовать естественный синтаксис `a * b`.

Вопрос: почему скалярное произведение возвращает число?

Ответ: по определению dot product сумма произведений координат является скаляром.

# Лабораторная 3: исключения, файлы, обработка данных

## Суть лабораторной

Третья лабораторная — это уже маленькое консольное приложение.

Задача: прочитать финансовые отчёты из папки `data`, поддержать CSV и JSON, проверить записи, собрать ошибки, посчитать суммы по категориям и сохранить результат в `result.json`.

Файл запуска:

```text
second_semestr/lab_3/main.py
```

Структура проекта:

```text
app/core      модели и исключения
app/io        чтение файлов
app/services  валидация и агрегация
main.py       точка входа
```

Главная теория здесь:

- исключения;
- отказоустойчивость;
- разделение ответственности;
- логирование;
- работа с файлами;
- атомарная запись.

## Что такое исключение

Исключение — это механизм Python для обработки ошибок.

Пример:

```python
raise ValidationError("amount должен быть > 0")
```

`raise` выбрасывает ошибку.

`try/except` позволяет её поймать:

```python
try:
    validate(record)
except ValidationError as e:
    errors.append(str(e))
```

Если исключение не поймать, программа завершится traceback-ом.

## Почему нельзя просто везде использовать `Exception`

Можно, но это плохой стиль.

Если всё ловить как `Exception`, сложно понять, что именно произошло:

- файл битый;
- данных не хватает;
- сумма отрицательная;
- диск не даёт записать файл;
- ошибка в коде.

Кастомные исключения делают ошибки понятными и управляемыми.

## Кастомные исключения

В проекте есть:

```python
class BaseAppError(Exception):
    pass

class DataFormatError(BaseAppError):
    pass

class ValidationError(BaseAppError):
    pass
```

Смысл:

- `BaseAppError` — общий родитель ошибок приложения;
- `DataFormatError` — ошибка структуры или формата файла;
- `ValidationError` — ошибка конкретной записи;
- `CurrencyMismatchError` — специальная бизнес-ошибка для валют.

Почему это удобно:

```python
except BaseAppError:
```

может поймать все ожидаемые ошибки приложения, но не скрывать совсем неожиданные системные проблемы.

## DataFormatError и ValidationError

Разница важная.

`DataFormatError` — проблема с файлом или его структурой:

- CSV пустой;
- в CSV нет нужных колонок;
- JSON битый;
- JSON не является списком.

`ValidationError` — файл читается, но конкретная запись нарушает правила:

- нет поля `amount`;
- `amount` не число;
- `amount <= 0`;
- пустой `id`;
- пустая категория.

Пример ответа:

Форматная ошибка относится к способу хранения данных, а валидационная — к бизнес-смыслу записи.

## Fail fast

Fail fast — принцип, при котором программа сразу останавливается, если дальше работать опасно или бессмысленно.

Пример из лабораторной:

Если входной директории нет, программа не может обработать данные. Поэтому она пишет ошибку и завершает работу.

Это лучше, чем молча создать пустой результат и сделать вид, что всё нормально.

## Graceful degradation

Graceful degradation — программа продолжает работать частично, если часть данных испорчена.

Пример:

В папке 10 файлов. Один JSON битый, а остальные нормальные. Правильное поведение — обработать 9 файлов, записать ошибку по битому и выдать частичный результат.

То же со строками:

Если в CSV одна строка с отрицательной суммой, не надо валить весь файл. Эту строку можно пропустить, залогировать и обработать остальные.

## Слоистая архитектура

Слоистая архитектура означает, что разные части программы отвечают за разные задачи.

В лабораторной:

### `app/io`

Отвечает за чтение файлов.

CSV-reader знает, как читать CSV.

JSON-reader знает, как читать JSON.

Он не должен решать, хорошая ли сумма у транзакции.

### `app/services/validator.py`

Отвечает за проверку бизнес-правил.

Например:

- все поля есть;
- `amount` приводится к `float`;
- `amount > 0`.

### `app/services/aggregator.py`

Отвечает за итоговую агрегацию:

```text
food -> 150.0
rent -> 200.0
```

### `app/core`

Хранит базовые сущности:

- модель `Transaction`;
- исключения.

## Почему разделение важно

Если весь код написать в одном `main.py`, то:

- сложно тестировать;
- сложно добавлять новый формат;
- сложно найти ошибку;
- сложно переиспользовать код.

При разделении можно отдельно тестировать чтение, отдельно валидацию, отдельно агрегацию.

## Registry pattern

Registry pattern — это способ связать ключ с обработчиком.

В проекте ключ — расширение файла:

```python
READERS = {
    ".csv": read_csv,
    ".json": read_json,
}
```

Когда программа видит файл `.csv`, она берёт `read_csv`.

Когда видит `.json`, берёт `read_json`.

Плюс такого подхода: чтобы добавить XML, достаточно написать `read_xml` и добавить:

```python
".xml": read_xml
```

Не нужно переписывать основную логику.

## Валидация данных

Валидация — проверка данных перед использованием.

В лабораторной запись должна иметь поля:

- `id`;
- `amount`;
- `category`;
- `date`.

`amount` должен быть числом и быть больше нуля.

Почему это важно:

Если не проверять данные, программа может:

- неправильно посчитать итог;
- упасть в неожиданном месте;
- записать мусорный результат.

## Логирование

`logging` — стандартный модуль Python для логов.

Он лучше `print`, потому что:

- можно писать в файл;
- есть уровни важности;
- есть время события;
- можно отключать или настраивать вывод;
- подходит для production-кода.

Уровни:

- `DEBUG` — подробная отладка;
- `INFO` — обычное событие;
- `WARNING` — проблема, но программа продолжает работать;
- `ERROR` — операция завершилась ошибкой;
- `CRITICAL` — серьёзная проблема.

В лабораторной ошибки пишутся в `app.log`.

## Атомарная запись

Атомарная запись здесь означает:

1. Сначала записать результат во временный файл.
2. Потом заменить основной файл через `os.replace`.

Зачем:

Если программа упадёт на середине записи, основной `result.json` не будет испорчен.

Плохой вариант:

```python
open("result.json", "w")
```

Если запись оборвётся, файл может остаться пустым или неполным.

Хороший вариант:

```text
result.json.tmp -> result.json
```

## Частые вопросы по лабе 3

Вопрос: почему ошибка одной строки не останавливает программу?

Ответ: это ожидаемая ошибка данных. Мы хотим обработать все корректные записи, а плохие записать в отчёт.

Вопрос: зачем `pathlib`, если есть `os.path`?

Ответ: `pathlib.Path` даёт объектный и более читаемый способ работать с путями: `path.suffix`, `path.open()`, `path.iterdir()`.

Вопрос: почему `amount` приводится к `float`?

Ответ: данные из CSV/JSON могут прийти строкой, а для подсчёта суммы нужно число.

# Лабораторная 4: автоматизированное тестирование

## Суть лабораторной

В четвёртой лабораторной нужно покрыть тестами проект из лабораторной 3.

Тесты лежат в:

```text
second_semestr/lab_4/tests/
```

Есть:

- unit-тесты;
- integration-тесты;
- фикстуры;
- параметризация;
- mock через `unittest.mock.patch`;
- coverage через `pytest-cov`.

## Зачем нужны тесты

Тесты нужны не только чтобы найти ошибки сейчас. Главная польза — защита от поломок в будущем.

Когда проект меняется, тесты быстро показывают, что старая логика всё ещё работает.

Без тестов программист проверяет всё руками. Это:

- медленно;
- легко забыть кейс;
- сложно повторять;
- плохо масштабируется.

## Unit-тесты

Unit-тест проверяет маленькую часть программы изолированно.

Пример:

Проверить функцию `validate`:

- сумма `0.01` валидна;
- сумма `0` невалидна;
- сумма `abc` невалидна;
- нет поля `id` — ошибка.

Плюс unit-теста:

- быстрый;
- легко понять, что сломалось;
- не требует реальных файлов, сети, базы.

## Integration-тесты

Integration-тест проверяет совместную работу нескольких частей.

Например:

1. Создать CSV.
2. Прочитать его.
3. Провалидировать строки.
4. Агрегировать результат.
5. Проверить итоговый JSON.

Такой тест ближе к реальному использованию программы.

Минус: если он упал, иногда сложнее понять, в каком именно слое проблема.

## Test pyramid

Пирамида тестирования:

- много unit-тестов;
- меньше integration-тестов;
- ещё меньше e2e-тестов.

Почему так:

Unit-тесты быстрые и точные, поэтому их должно быть больше.

E2E-тесты полезные, но медленнее и сложнее.

## AAA

AAA — стандартная структура теста.

### Arrange

Подготовка данных.

Например, создать словарь:

```python
record = {"id": "1", "amount": "100", ...}
```

### Act

Вызвать тестируемую функцию:

```python
tx = validate(record)
```

### Assert

Проверить результат:

```python
assert tx.amount == 100.0
```

Почему это важно:

Тест становится читаемым. Понятно, что подготовили, что вызвали и что ожидаем.

## Fixtures

Фикстура — функция, которая подготавливает данные для тестов.

В pytest фикстуры пишутся через:

```python
@pytest.fixture
def good_record():
    return {...}
```

Плюсы:

- не дублируем подготовку данных;
- тесты короче;
- общие данные проще менять.

## `tmp_path`

`tmp_path` — встроенная фикстура pytest. Она создаёт временную папку.

Зачем:

- можно создавать тестовые файлы;
- не засоряется проект;
- после теста временные файлы удаляются;
- тесты не зависят от реальной папки `data`.

Пример:

```python
def test_something(tmp_path):
    file = tmp_path / "test.csv"
    file.write_text("...")
```

## Parametrize

Параметризация позволяет одним тестом проверить много наборов данных.

Пример:

```python
@pytest.mark.parametrize("amount, valid", [
    ("0.01", True),
    ("0", False),
    ("abc", False),
])
```

Без параметризации пришлось бы писать много почти одинаковых тестов.

Плюс:

- меньше дублирования;
- проще добавить новый кейс;
- отчёт pytest покажет, на каком параметре упало.

## Mock и patch

Mock — объект-заглушка, который заменяет реальный объект.

`patch` временно подменяет функцию, метод или объект.

В лабораторной 4 есть:

```python
from unittest.mock import patch
```

И тест:

```python
with patch("main.os.replace", side_effect=OSError("read-only filesystem")):
```

Что это значит:

Мы временно заменяем `os.replace` так, будто он падает с ошибкой диска.

Зачем:

Не надо реально ломать права доступа или портить файловую систему. Мы безопасно проверяем редкую ошибку.

Это и есть mocking: контролируемая имитация внешнего поведения.

## Spy

Во втором тесте `patch` используется как spy: мы не просто ломаем функцию, а смотрим, с какими аргументами она была вызвана.

Так проверяется, что `save_result` сначала пишет `.tmp`, а потом вызывает `os.replace`.

## Coverage

Coverage показывает, какая часть кода была выполнена во время тестов.

Например, coverage 87% означает, что 87% строк были пройдены тестами.

Но coverage не гарантирует правильность.

Можно выполнить строку кода, но не проверить правильный результат.

Хороший ответ:

Coverage — полезный индикатор, но качество тестов важнее процента.

## Частые вопросы по лабе 4

Вопрос: зачем нужны негативные тесты?

Ответ: программа должна правильно работать не только на хороших данных, но и на ошибках: битый JSON, плохая сумма, невозможность записи.

Вопрос: где здесь mock?

Ответ: в `tests/integration/test_save_failure.py`, где через `patch` подменяется `main.os.replace`.

Вопрос: почему тесты используют `tmp_path`, а не папку `data`?

Ответ: чтобы тесты были изолированными и не зависели от реальных файлов проекта.

# Лабораторная 5: ленивые вычисления и Big Data

## Суть лабораторной

Пятая лабораторная — рефакторинг проекта из третьей лабораторной под большие данные.

Проблема:

Если файл очень большой, нельзя загрузить все строки в память.

Цель:

Обрабатывать данные потоково: читать, валидировать и агрегировать по одному элементу.

## Проблема `readlines()`

Плохой подход:

```python
lines = file.readlines()
```

Он загружает весь файл в список строк.

Если файл весит 10 ГБ, программа попытается держать всё в памяти. Это может привести к:

- сильному торможению;
- `MemoryError`;
- завершению процесса операционной системой.

## Eager evaluation и lazy evaluation

Eager evaluation — жадные вычисления. Всё считается сразу.

Пример:

```python
data = list(reader)
```

Все элементы сразу попали в память.

Lazy evaluation — ленивые вычисления. Элемент создаётся только тогда, когда он нужен.

Пример:

```python
for row in reader:
    process(row)
```

Обрабатывается одна строка, потом следующая.

## Iterable и Iterator

Iterable — объект, по которому можно пройтись циклом `for`.

Iterator — объект, который отдаёт элементы по одному и помнит своё состояние.

У итератора есть:

```python
__iter__()
__next__()
```

Пример:

```python
items = iter([1, 2, 3])
next(items)  # 1
next(items)  # 2
```

## Генератор

Генератор — функция, в которой есть `yield`.

Пример:

```python
def numbers():
    yield 1
    yield 2
    yield 3
```

Когда вызываем `numbers()`, тело функции не выполняется сразу. Возвращается генератор.

Каждый `next()` выполняет функцию до следующего `yield`.

Главная польза:

Генератор не хранит все значения сразу.

## `yield from`

`yield from` передаёт значения из другого генератора.

Пример:

```python
def outer():
    yield from inner()
```

Это удобнее, чем:

```python
for item in inner():
    yield item
```

В лабораторной это используется для сборки потоков чтения и валидации.

## Pipeline

Pipeline — это конвейер обработки данных.

В лабораторной:

```text
файл -> reader -> validate_stream -> aggregate_by_category -> result.json
```

Каждый этап получает элемент, обрабатывает его и отдаёт дальше.

Плюс:

В памяти не лежит весь список транзакций.

## Потоковая агрегация

Агрегация по категориям не требует хранить все транзакции.

Пример:

Пришла транзакция:

```text
category = food
amount = 100
```

Мы делаем:

```python
totals["food"] += 100
```

После этого сама транзакция больше не нужна.

В памяти остаётся только словарь:

```python
{
    "food": 150.0,
    "rent": 200.0,
}
```

## O(1) и O(K) по памяти

Строго говоря, память здесь O(K), где K — число категорий.

Если категорий мало и они заранее ограничены, можно практически считать, что память постоянная относительно числа строк.

Важно:

Память не растёт от количества транзакций напрямую.

## Потоковое чтение CSV

`csv.DictReader` читает файл построчно.

Он не обязан загружать весь CSV в память.

Каждая строка превращается в словарь:

```python
{
    "id": "1",
    "amount": "100",
    "category": "food",
    "date": "2025-09-01",
}
```

## Потоковое чтение JSON

Обычный `json.load(f)` загружает весь JSON в память.

Для маленьких файлов это нормально, но для Big Data плохо.

В доработанной лабе 5 JSON-reader читает файл кусками и через `JSONDecoder.raw_decode` выдаёт объекты из массива постепенно.

Это сложнее, чем CSV, потому что JSON-массив синтаксически является одной большой структурой:

```json
[
  {"id": "1"},
  {"id": "2"}
]
```

Поэтому потоковый JSON требует аккуратного парсинга.

## `tracemalloc`

`tracemalloc` — модуль стандартной библиотеки Python для измерения памяти, выделенной Python-кодом.

Основные шаги:

```python
tracemalloc.start()
...
current, peak = tracemalloc.get_traced_memory()
tracemalloc.stop()
```

`peak` показывает максимальное потребление памяти во время работы.

В лабораторной это нужно, чтобы доказать: при большом файле память не растёт линейно с количеством строк.

## Генератор большого CSV

`generate_big_data.py` создаёт большой CSV для проверки.

Зачем:

Нужно не просто сказать “код потоковый”, а проверить его на большом файле и показать память через `--profile`.

## Частые вопросы по лабе 5

Вопрос: почему генератор экономит память?

Ответ: он отдаёт элементы по одному и не создаёт список всех элементов.

Вопрос: почему агрегация может быть потоковой?

Ответ: для каждой записи достаточно обновить сумму категории. Старую запись хранить не нужно.

Вопрос: почему JSON сложнее читать потоково, чем CSV?

Ответ: CSV естественно состоит из независимых строк, а JSON-массив является одной общей структурой.

Вопрос: что будет, если категорий миллион?

Ответ: память вырастет, потому что словарь сумм хранит каждую категорию. O(K), где K — число категорий.

# Лабораторная 6: асинхронное программирование

## Суть лабораторной

Шестая лабораторная сравнивает синхронное и асинхронное выполнение сетевых запросов.

Синхронная версия:

- использует `requests`;
- идёт по URL по одному;
- ждёт каждый ответ полностью.

Асинхронная версия:

- использует `aiohttp`;
- создаёт много корутин;
- запускает их конкурентно через `asyncio.gather`;
- ограничивает параллельность через `Semaphore`.

## CPU-bound и I/O-bound

CPU-bound — задача упирается в процессор.

Примеры:

- сложные вычисления;
- обработка изображений;
- машинное обучение на CPU;
- архивация.

I/O-bound — задача упирается в ожидание ввода-вывода.

Примеры:

- HTTP-запросы;
- чтение с диска;
- запросы к базе данных;
- ожидание ответа API.

Сетевые запросы обычно I/O-bound: процессор почти ничего не делает, он ждёт ответ сервера.

## Синхронное выполнение

Синхронный код работает последовательно:

```text
запрос 1 -> ждём -> запрос 2 -> ждём -> запрос 3 -> ждём
```

Если один запрос занимает 300 мс, 100 запросов могут занять около 30 секунд.

## Асинхронное выполнение

Асинхронный код может начать много запросов и переключаться между ними:

```text
запрос 1 отправлен
запрос 2 отправлен
запрос 3 отправлен
пока все ждут сеть, event loop не блокируется
```

Если 100 запросов выполняются конкурентно, общее время может быть близко к времени самых медленных запросов, а не к сумме всех времен.

## Асинхронность не равна параллелизму

Это важный вопрос на защите.

Асинхронность — это конкурентность. Она позволяет переключаться между задачами, когда они ждут I/O.

Параллелизм — это реальное одновременное выполнение, например на нескольких ядрах CPU.

В `asyncio` обычно один поток и один event loop.

## Event loop

Event loop — цикл событий.

Он:

- запускает корутины;
- видит, где корутина дошла до `await`;
- приостанавливает её;
- запускает другие корутины;
- возвращается к первой, когда операция завершилась.

Простыми словами:

Event loop — диспетчер асинхронных задач.

## Корутина

Корутина — функция, объявленная через `async def`.

Пример:

```python
async def fetch_url(...):
    ...
```

Вызов корутины не выполняет её сразу:

```python
fetch_url(...)
```

возвращает coroutine object.

Чтобы выполнить корутину, её надо:

- `await`;
- передать в `asyncio.gather`;
- запустить через `asyncio.run`.

## `await`

`await` используется внутри `async def`.

Он означает:

Эта операция может занять время, можно приостановить текущую корутину и дать event loop выполнять другие задачи.

Пример:

```python
data = await response.json()
```

Пока данные читаются из сети, event loop может заниматься другими запросами.

## `asyncio.run`

`asyncio.run(main_async(...))` создаёт event loop, запускает главную корутину и закрывает loop после завершения.

Обычно используется в точке входа программы.

## `asyncio.gather`

`gather` принимает несколько корутин и ждёт их завершения.

Пример:

```python
results = await asyncio.gather(*tasks)
```

Это позволяет запустить много запросов конкурентно.

## `aiohttp.ClientSession`

`ClientSession` — объект HTTP-сессии.

Почему не создавать новую сессию на каждый запрос:

- это медленнее;
- хуже переиспользуются соединения;
- больше нагрузка на систему.

Правильный подход:

```python
async with aiohttp.ClientSession() as session:
    ...
```

Одна сессия используется для многих запросов.

## Semaphore

`asyncio.Semaphore` ограничивает количество одновременных операций.

Зачем:

Если сразу отправить 1000 запросов:

- можно получить HTTP 429 Too Many Requests;
- можно превысить лимит открытых сокетов;
- можно перегрузить сервер;
- можно получить нестабильные результаты.

Семафор говорит:

Одновременно выполняется не больше N запросов.

Пример:

```python
async with semaphore:
    ...
```

Когда задача входит в блок, она занимает слот. Когда выходит — освобождает.

## Timeout

Timeout ограничивает время ожидания.

Если сервер завис, программа не должна ждать бесконечно.

В лабораторной используется `aiohttp.ClientTimeout`.

Если запрос слишком долгий, ловится `asyncio.TimeoutError`, ошибка логируется, а функция возвращает `{}`.

## Обработка ошибок

При массовых сетевых запросах ошибки нормальны:

- сервер недоступен;
- таймаут;
- HTTP 500;
- HTTP 404;
- соединение оборвалось.

Правильная программа не должна падать целиком из-за одного URL.

Поэтому `fetch_url` возвращает пустой словарь `{}` для проблемного запроса.

## Почему нельзя использовать `requests` внутри `async def`

`requests.get()` — блокирующий вызов.

Если вызвать его внутри асинхронной функции, он заблокирует весь поток и весь event loop.

Тогда другие корутины не смогут выполняться, пока `requests.get()` ждёт сеть.

Правильный async HTTP-клиент — `aiohttp`.

## Частые вопросы по лабе 6

Вопрос: почему async быстрее для сети?

Ответ: потому что программа не простаивает во время ожидания ответа одного запроса, а запускает и обслуживает другие запросы.

Вопрос: async ускорит тяжёлые вычисления?

Ответ: нет, для CPU-bound задач лучше multiprocessing, нативные библиотеки или оптимизация алгоритма.

Вопрос: зачем возвращать `{}` при ошибке?

Ответ: чтобы один плохой URL не сорвал сбор всех данных.

Вопрос: зачем сравнивать sync и async?

Ответ: чтобы показать практическую разницу во времени на I/O-bound задаче.

# Лабораторная 7: Git

## Суть лабораторной

Седьмая лабораторная — прохождение Learn Git Branching.

Главная цель — понять модель Git:

- коммиты;
- ветки;
- HEAD;
- merge;
- rebase;
- удалённые репозитории;
- fetch/pull/push.

## Что такое Git

Git — распределённая система контроля версий.

Она хранит историю изменений проекта.

Git позволяет:

- возвращаться к старым версиям;
- работать в ветках;
- сравнивать изменения;
- объединять работу нескольких людей;
- отправлять код в удалённый репозиторий.

## Commit

Commit — снимок состояния проекта.

У коммита есть:

- hash;
- автор;
- дата;
- сообщение;
- ссылка на родительский коммит;
- набор изменений.

Коммиты образуют граф, а не просто список.

## Branch

Branch — это указатель на коммит.

Важно:

Ветка — не копия проекта, а лёгкий указатель.

Когда мы делаем новый commit в ветке, указатель ветки передвигается на новый commit.

## HEAD

`HEAD` показывает, где мы сейчас находимся.

Обычно `HEAD` указывает на текущую ветку.

Если checkout сделать на конкретный commit, может быть detached HEAD.

Detached HEAD означает, что мы не на ветке, а прямо на коммите.

## Checkout и switch

`git checkout` исторически делает много разных вещей:

- переключает ветки;
- восстанавливает файлы;
- переходит на commit.

`git switch` — более новая команда для переключения веток.

Пример:

```bash
git switch main
```

## Merge

Merge объединяет две ветки.

Если история простая, Git может сделать fast-forward: просто передвинуть указатель ветки.

Если ветки расходились, Git создаёт merge commit.

Плюс merge:

Сохраняется реальная история ветвления.

Минус:

История может быть менее линейной.

## Rebase

Rebase переносит коммиты текущей ветки поверх другой базы.

Пример:

Было:

```text
main:    A---B
feature: A---C---D
```

После rebase feature на main:

```text
main:    A---B
feature:     C'---D'
```

Коммиты `C` и `D` становятся новыми коммитами `C'` и `D'`, потому что у них изменился родитель.

Плюс:

История становится линейной.

Минус:

Rebase переписывает историю.

## Merge vs rebase

Короткий ответ:

`merge` сохраняет историю ветвления, `rebase` переписывает историю так, будто работа начиналась от более свежего коммита.

Когда использовать merge:

- когда важно сохранить реальную историю;
- при объединении публичных веток;
- когда команда так договорилась.

Когда использовать rebase:

- чтобы обновить свою локальную feature-ветку перед merge;
- чтобы сделать историю чище;
- если ветка ещё не используется другими людьми.

Почему нельзя бездумно rebase публичной ветки:

Другие люди могут уже основываться на старых коммитах. После rebase hash коммитов изменится, и у коллег появятся конфликты истории.

## Cherry-pick

`cherry-pick` переносит конкретный коммит в текущую ветку.

Это полезно, если нужна не вся ветка, а один конкретный фикс.

Пример:

```bash
git cherry-pick abc123
```

## `^` и `~`

В Git можно ссылаться на родителей коммитов.

`HEAD^` — первый родитель текущего коммита.

`HEAD~1` — на один коммит назад.

`HEAD~3` — на три коммита назад по первому родителю.

Для merge commit `^2` может означать второго родителя.

## Remote repository

Remote — удалённый репозиторий.

Обычно:

```text
origin
```

Это не магическое имя, просто стандартное название remote по умолчанию.

## `origin/main`

`origin/main` — remote-tracking branch.

Это локальный указатель на то, где была ветка `main` в remote во время последнего `fetch` или `pull`.

Важно:

`origin/main` не обновляется само постоянно. Его надо обновлять через `fetch` или `pull`.

## Fetch

`git fetch` скачивает данные из remote, но не меняет текущую рабочую ветку.

Это безопасная команда для посмотреть, что изменилось на сервере.

## Pull

`git pull` — это `fetch` плюс интеграция изменений.

Обычно это:

```text
git fetch + git merge
```

Но может быть настроено как:

```text
git fetch + git rebase
```

## Push

`git push` отправляет локальные коммиты в remote.

Если remote ушёл вперёд, push может быть отклонён. Тогда надо сначала забрать изменения через pull/fetch и решить расхождения.

## Конфликт

Конфликт возникает, когда Git не может автоматически объединить изменения.

Например:

Два человека поменяли одну и ту же строку по-разному.

Тогда надо вручную выбрать правильный вариант, отметить файл как решённый и продолжить merge/rebase.

## Частые вопросы по лабе 7

Вопрос: Git хранит изменения или снимки?

Ответ: концептуально Git хранит снимки состояния проекта, а не просто последовательность diff-ов.

Вопрос: ветка — это копия проекта?

Ответ: нет, ветка — это указатель на коммит.

Вопрос: чем `fetch` отличается от `pull`?

Ответ: `fetch` только скачивает изменения, `pull` скачивает и сразу пытается применить их к текущей ветке.

Вопрос: что такое detached HEAD?

Ответ: состояние, когда `HEAD` указывает напрямую на коммит, а не на ветку.

Вопрос: почему rebase меняет hash коммитов?

Ответ: потому что hash зависит от содержимого коммита и его родителя. При rebase родитель меняется, значит меняется и hash.

# Быстрые ответы на самые вероятные вопросы

## Почему код разделён на модули?

Чтобы у каждой части была своя ответственность. Чтение файлов, валидация, агрегация и запуск программы — разные задачи. Так код проще тестировать, менять и расширять.

## Почему не использовать `print` для ошибок?

`print` просто выводит текст. `logging` даёт уровни, время, запись в файл и нормальную настройку вывода.

## Почему нужны тесты, если программа запускается?

Один ручной запуск проверяет только один сценарий. Тесты автоматически проверяют много сценариев, включая ошибки и граничные значения.

## Почему генераторы важны для Big Data?

Потому что они не хранят весь набор данных в памяти. Они отдают элементы постепенно.

## Почему async быстрее для HTTP?

Потому что HTTP-запросы большую часть времени ждут сеть. Async позволяет во время ожидания одного запроса выполнять другие.
